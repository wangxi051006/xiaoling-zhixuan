# 批量配送接口与测试

本文记录 2026-11-14 当前共用后端的接口契约与已执行验证，供商家端、骑手端和用户端联调使用。本文不是总验收结论；原始测试日志、后续全量集成结果和浏览器验证，以主代理最终报告为准。

## 业务行为与范围

正常送达不再需要买家生成、提供或输入签收码。骑手开始配送后，在订单指定配送点取得有效定位凭据，再直接确认送达。用户无需配合完成确认操作。

原 `GET /api/v1/orders/{id}/receipt-code` 返回 HTTP 410，错误码为 `RECEIPT_CODE_RETIRED`。旧验证码生成与校验业务代码已移除；历史迁移、表和审计证据保留。客户端不得再提交旧 `code` 字段。

本版支持批量接单、批量核对取货、同一配送点批量送达。批量动作只支持 `CLAIM`、`PICKUP`、`COMPLETE`，不包含批量 `START`。取货后仍须通过现有单笔 `/start` 进入配送中。

## 通用约定

- 以下接口统一以 `/api/v1` 为前缀；表格中的路径省略该前缀。
- ID 使用字符串；`version`、`expectedVersion` 为正整数。客户端须使用服务端返回的任务版本。
- 骑手接口需要有效登录令牌和当前门店 `courier` 权限；配送点管理接口需要 `dispatch` 权限。
- 正常业务数据放在统一 JSON 响应的 `data` 中；错误包含 `code`、`message` 和 `traceId`。批次执行中断或凭据过期时，错误响应仍可包含 `data` 中的已持久化进度，客户端应读取它。
- 配送命令和批次的 `requestId` 为 16–128 位字母、数字、下划线或连字符。若发送 `Idempotency-Key` 请求头，其值必须与请求体 `requestId` 一致。
- 对网络断开、超时等结果未知的请求，保留原请求编号和原参数，先查询或重放原请求。

## 配送点配置与订单快照

首版每个门店的每栋楼只配置一个默认配送点，由数据库唯一约束 `store_id + building_id` 保证。不同地址不能通过楼名或地址文本相似性合并。本版没有一楼多点选择功能。

| 方法与路径 | 权限与用途 | 返回 `data` |
| --- | --- | --- |
| `GET /delivery-points?buildingId=...` | 公开读取当前门店启用的配送点；`buildingId` 可省略 | 配送点数组 |
| `GET /admin/delivery-points?buildingId=...` | `dispatch`；读取本门店全部配置 | 配送点数组 |
| `POST /admin/delivery-points` | `dispatch`；创建楼栋默认点 | 保存后的配送点 |
| `PUT /admin/delivery-points/{id}` | `dispatch`；修改已有点 | 保存后的配送点 |

配送点对象字段：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `id` | string | 服务端生成的配送点 ID |
| `buildingId` | string | 必须属于当前门店；已有配送点不能移到其他楼栋 |
| `name` | string | 去除首尾空白后 1–80 个字符 |
| `latitude` | number | WGS84 纬度，范围 `[-90, 90]`，必须明确提供 |
| `longitude` | number | WGS84 经度，范围 `[-180, 180]`，必须明确提供 |
| `radiusMeters` | integer | 到达范围半径，20–300 米 |
| `active` | boolean | 是否启用；保存时省略默认为 `true` |
| `version` | integer | 配置版本，创建后为 1，修改成功递增 |

POST 请求发送 `buildingId`、`name`、`latitude`、`longitude`、`radiusMeters`、`active`，不发送返回对象的 `id`。PUT 发送同样字段并携带当前 `version`；兼容 `expectedVersion`，两者同时存在且 `version` 非零时以 `version` 为准。版本过旧返回 `VERSION_CONFLICT`。同楼重复创建返回 `DELIVERY_POINT_EXISTS`。

配送订单创建时，如已有明确启用的配送点，就把完整对象保存到 `orders.address_json.deliveryPoint`。后续修改配送点不会悄悄改写既有订单快照。

历史订单没有快照时，只能按该订单原始 `buildingId` 匹配商家明确配置的启用点；到达校验成功时，在事务内把该点保存进订单快照。未配置时返回 `DELIVERY_POINT_REQUIRED`，不能猜测坐标，也不能按地址字符串绑定。当前允许未配置配送点的订单创建，但此类订单不能确认送达，直至商家完成明确配置。

任务查询新增 `deliveryPointId`、`deliveryPointName`、`latitude`、`longitude`、`radiusMeters`。没有配置时这些字段可能省略。历史订单查询可展示楼栋当前默认点，但最终以到达校验事务保存的快照为准。

## 状态前提：严格要求配送中

状态流转为：

```text
OPEN → CLAIM/指派 → ACCEPTED
ACCEPTED + 订单 READY + checked=true → PICKED_UP
PICKED_UP + 订单 READY → START → DELIVERING
DELIVERING + 有效到达凭据 → COMPLETED
```

`arrival` 与 `complete` 都要求任务状态为 `DELIVERING`、订单状态为 `DELIVERING`，并且已存在取货时间 `picked_at`。仅取货但未开始配送的任务不能送达。异常任务必须先恢复到符合要求的状态。完成命令还校验订单支付状态允许履约，不改变库存或支付结算逻辑。

## 到达定位与凭据

| 方法与路径 | 请求体 | 返回 `data` |
| --- | --- | --- |
| `POST /courier/tasks/{id}/arrival` | `latitude`、`longitude`、`accuracy`、`observedAt` | 到达凭据对象 |
| `POST /courier/arrivals` | 上述字段，加 `taskIds: string[]`，1–20 个任务 | 到达凭据对象 |

`observedAt` 使用带时区的 ISO 8601/RFC3339 时间。`accuracy` 单位为米。服务端实际校验规则：

| 校验项 | 当前规则 |
| --- | --- |
| 坐标系 | WGS84；经纬度必须为有效有限数值且在合法范围内 |
| 定位时间 | 距服务端当前时间不超过 60 秒；最多允许快于服务端 15 秒 |
| 定位精度 | `0 < accuracy <= min(50, radiusMeters)` |
| 距离 | 用经纬度计算球面距离，距离不得大于配送点快照的 `radiusMeters` |
| 到达凭据有效期 | 服务端签发后 120 秒；以返回的 `expiresAt` 为准 |
| 权限与状态 | 当前门店、当前骑手、有效成员和角色、任务当前分配及配送中状态 |

到达凭据响应结构：

```json
{
  "arrivalToken": "服务端签名凭据",
  "expiresAt": "2026-11-14T04:02:00Z",
  "deliveryPointId": "12",
  "deliveryPointName": "楼栋入口取货架",
  "taskIds": ["101", "102"]
}
```

以上仅为结构示例，不代表真实配送点或可使用的凭据。服务端使用 HMAC 签名，绑定门店、骑手、任务 ID、任务分配代次、配送点快照摘要及过期时间。凭据不由客户端自行生成，不能转给其他骑手或用于未绑定任务。

批量到达要求所有任务拥有同一配送点和同一配置快照。相同 `id` 但不同 `version`、名称、坐标或范围，也不作为同一快照处理；返回 `MIXED_DELIVERY_POINTS` 后应拆分操作。

## 单笔确认送达

`POST /courier/tasks/{id}/complete`

```json
{
  "requestId": "courier_complete_000001",
  "expectedVersion": 4,
  "arrivalToken": "此前 arrival 返回的凭据"
}
```

成功返回 `data: {"ok":true,"taskId":"101","status":"COMPLETED","version":5}`，版本值由服务端状态决定。

成功结果与任务状态在同一事务保存。同一请求的成功重放在到达凭据过期后仍可返回原成功结果，不重复完成、不重复释放容量、不重复通知；当前权限和任务归属仍先行检查。改派后的旧骑手不能利用旧成功请求取得操作权。

单笔 `ARRIVAL_EXPIRED` 等校验失败会回滚本次事务，不保存成功幂等结果。收到明确失败后可重新定位，使用新请求编号和当前版本提交；结果未知时应先重放原请求，避免把未知成功误当作失败。

## 骑手批量操作

| 方法与路径 | 用途 |
| --- | --- |
| `POST /courier/tasks/batch-actions` | 创建或重放原批次并执行 |
| `GET /courier/tasks/batch-actions?requestId=...` | 丢失提交响应时按原请求编号找回批次及进度 |
| `GET /courier/tasks/batch-actions/{id}` | 查询当前骑手自己的批次 |
| `POST /courier/tasks/batch-actions/{id}/resume` | 从持久化目标和结果恢复原批次 |

提交结构：

```json
{
  "requestId": "courier_batch_pickup_00001",
  "action": "PICKUP",
  "items": [
    {"taskId": "101", "expectedVersion": 2},
    {"taskId": "102", "expectedVersion": 2}
  ],
  "checked": true
}
```

动作差异：

| `action` | 要求 |
| --- | --- |
| `CLAIM` | 任务开放且未分配，订单可履约，骑手在线且剩余容量足够 |
| `PICKUP` | 本骑手已接受任务、商家订单 `READY`，且请求 `checked=true` |
| `COMPLETE` | 严格 `DELIVERING`；请求添加同地点批量到达返回的 `arrivalToken` |

每批 1–20 项，重复 `taskId` 被拒绝。列表会按任务 ID 标准化排序。请求指纹包含动作、任务及版本、核对标志和原到达凭据；同一门店与骑手下，同一 `requestId` 更换动作或参数返回 HTTP 409 `IDEMPOTENCY_CONFLICT`。

骑手批次使用独立的 `courier_batches`、`courier_batch_items` 表，不复用商家批量操作的权限和结果表。

批次返回 `data` 结构：

```json
{
  "batchId": "8",
  "requestId": "courier_batch_pickup_00001",
  "action": "PICKUP",
  "status": "DONE",
  "expectedCount": 2,
  "completedCount": 2,
  "pendingCount": 0,
  "successCount": 1,
  "failedCount": 1,
  "items": [
    {"taskId":"101","expectedVersion":2,"result":"SUCCESS","code":"","message":"操作成功","version":3},
    {"taskId":"102","expectedVersion":2,"result":"FAILED","code":"ORDER_NOT_READY","message":"商家备齐且已接受任务后才能取货","version":0}
  ]
}
```

这是结构示例。`DONE` 表示每项都有终态，并不表示全部成功；客户端必须逐项呈现结果。

| 单项 `result` | 含义与恢复方式 |
| --- | --- |
| `SUCCESS` | 已提交成功，恢复时不重复修改状态 |
| `FAILED` | 确定的业务失败；原批次保留结果。条件修复后读取新版本并创建新批次 |
| `PENDING` | 尚未提交结果，或送达到达凭据需要更新；继续原批次 |

每项使用独立事务；任务状态、容量、事件、通知以及该项结果一起提交。业务失败使用事务保存点撤回该项部分写入，再持久化失败。数据库故障回滚当前项，停止本轮执行；此前成功项保留，未完成项仍可恢复。

批次全为终态时通常返回 HTTP 200，即使其中有 `FAILED`。定位凭据过期等可恢复错误返回 HTTP 409，并携带当前批次进度；数据库故障可返回 HTTP 500，其他未完成状态可返回 HTTP 503。不要只看 HTTP 状态判断是否已有订单完成。

## 原批次恢复

1. 用原 `requestId` 或 `batchId` 查询服务端结果。
2. 只有 `PENDING` 项需要继续执行，成功项保持原结果。
3. 对送达批次，若凭据过期，在原配送点对剩余任务重新获取定位，并调用 `/courier/arrivals`。
4. 调用 `POST /courier/tasks/batch-actions/{id}/resume`，请求体为 `{"arrivalToken":"新凭据"}`。非送达批次可发送 `{}`。

`resume` 只更新到达授权凭据，不修改原任务列表、预期版本、动作或请求指纹。重放原 POST 时仍发送原参数；不要把新凭据替换到相同 `requestId` 的原 POST 中。

`ARRIVAL_EXPIRED` 保留已成功项；恢复只执行剩余项。服务端在批次行锁下验证原凭据签名并比较配送点摘要，原凭据过期也不能借恢复更换地点。不同配送点的新凭据返回 `ARRIVAL_POINT_MISMATCH`，防止把多个地点串成一个送达批次。已完成批次重放或恢复不因原凭据过期而失效，但当前角色和任务归属仍会检查。

## 容量、改派与权限

`GET /courier/capacity` 返回：

```json
{"activeTaskCount":0,"taskLimit":3,"online":true}
```

上例表示当前没有活跃任务。容量行缺失时，`taskLimit` 默认为 3、`online` 默认为 `true`，但 `activeTaskCount` 仍查询该骑手实际任务数，不能默认为零。占用状态统一为 `ACCEPTED`、`PICKED_UP`、`DELIVERING`、`EXCEPTION`；异常任务仍占用容量，`OPEN`、`COMPLETED`、`CANCELLED` 不计入。

每批上限 20 不代表可同时接 20 单，当前默认容量仍为 3 单。接单、分配、改派和完成在事务内更新容量。容量行锁串行化同一骑手的容量增减；命令采用 `READ COMMITTED`，在取得容量锁后按真实活跃任务重新计数，避免旧任务缺少容量行或旧容量计数偏低导致超接。任务完成前先扣减容量，与任务状态更新共同提交。演示种子也按相同状态口径写入和修正容量。

迁移 `0012_courier_capacity_recovery.sql` 保留“计数非负、任务上限为正”的数据库约束，移除阻止记录历史超载的数据库上限约束。新增任务仍受事务行锁内的容量上限限制；已有五单而当前上限为三单时，禁止再接单，但允许完成后从五单减至四单、再减至三单，不会因仍然超载而阻止释放容量。

批次只能由创建它的当前门店骑手读取或恢复。员工/骑手角色停用会撤销接口访问权。任务归属在命令执行和成功重放前再次校验；改派后旧骑手不能继续执行或重放旧操作。凭据还绑定 `assignment_generation`，避免任务重新分配后旧到达证明继续有效。

## 通知事务

完成配送的同一事务会更新任务和订单、释放骑手容量、写入 `DELIVERY_COMPLETE` 事件，并调用 `enqueueDeliveryNotification`。

该方法持久化用户站内通知和 `DELIVERY_NOTIFICATION` outbox 事件，通知唯一事件键为 `DELIVERED:<orderId>`。内容使用订单配送点快照名称，告知用户前往领取。任何通知入库错误都会回滚该笔完成操作；成功重放不重复生成通知。

用户消息接口为 `GET /notifications`、`GET /notifications/stream` 和 `POST /notifications/{id}/read`。通知落库与用户终端实际收到推送是不同事实；本文的配送故障测试验证数据库事务和去重，不代表已验证外部短信、微信订阅消息或所有设备上的实时推送。

## 常见错误与客户端处理

| 错误码 | 含义与建议 |
| --- | --- |
| `DELIVERY_POINT_REQUIRED` | 原楼栋没有明确配送点；联系商家配置 |
| `INVALID_LOCATION` | 定位缺失、非有限数值或超出经纬度范围 |
| `LOCATION_STALE` | 定位超过 60 秒，或设备时间超出未来容忍范围；重新定位 |
| `LOCATION_INACCURATE` | 定位精度不满足要求；改善定位条件后重试 |
| `OUTSIDE_DELIVERY_POINT` | 服务端测距超出订单配送点范围 |
| `MIXED_DELIVERY_POINTS` | 批量到达包含不同点或不同快照；拆分任务 |
| `ARRIVAL_REQUIRED` / `ARRIVAL_INVALID` | 缺少或不合法的到达凭据 |
| `ARRIVAL_EXPIRED` | 凭据过期；保留成功项，在原点重新定位后恢复 |
| `ARRIVAL_TASK_MISMATCH` | 凭据不包含任务或分配代次不一致 |
| `ARRIVAL_POINT_MISMATCH` | 凭据与订单快照或原批次地点不一致 |
| `CAPACITY_EXCEEDED` | 骑手离线或当前容量已满 |
| `VERSION_CONFLICT` | 任务或配置已经变化；刷新后重新确认 |
| `ORDER_NOT_READY` / `ITEMS_NOT_CHECKED` | 尚未备齐或未确认核对商品 |
| `IDEMPOTENCY_CONFLICT` | 同一请求编号参数变化；先查询原结果 |
