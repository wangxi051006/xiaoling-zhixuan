# 校零智选 · 三端校园零售系统

一个真实跑通的校园零售交易系统：**商家接单履约、用户下单收货、骑手接单配送**，三端共用一套 Go + MySQL 后端，每端各配一套微信小程序。

> 起因是我自己在学校里做社群零售（月流水约 2 万元），订单、库存、对账全靠 Excel，人一多就乱。这个项目就是把那套流程变成系统。

## 功能概览

| 端 | 核心能力 |
| --- | --- |
| 商家端 | 商品与 SKU 管理、履约工作台、批量接单/出餐（单批 ≤50 单）、配送点设置、退款处理、报表 |
| 用户端 | 浏览下单、结算支付（模拟）、订单列表与详情、站内消息（SSE 在线提醒 + 断线补取） |
| 骑手端 | 任务列表、批量领取与取货（≤20 单）、开始配送、定位校验送达、异常上报 |
| 共用后端 | 认证与鉴权、订单/支付/库存状态机、幂等与事务、批量接口契约、迁移与审计 |

## 关键设计决策

**1. 幂等：同一 requestId 同参重放，异参返回 409**

移动端网络不稳，连点、超时重试都是常态。没有幂等就是重复下单、重复扣款。requestId 落库为唯一键，同参直接返回上次结果，参数不同判冲突而不是覆盖。批量接口还必须返回 `pendingCount: 0` 才算终态。

**2. 金额一律用整数分**

浮点做金额，0.1 + 0.2 ≠ 0.3，对账一定出问题，而且是"偶尔差一分钱"这种极难排查的问题。全链路整型，比较与结算不出现浮点元。

**3. 订单 / 库存 / 支付状态分离，写操作只走应用服务与事务**

禁止用通用 PATCH 直接改状态。取消订单时若支付状态是 UNKNOWN，不能"推定未付"然后释放库存——那会超卖，正确做法是保留库存预留并进入人工核实。

**4. 送达由服务端校验，不靠用户点确认**

商家配置真实 WGS84 配送点与允许半径（20–300 米），骑手到达后上报位置，服务端校验后再落库送达，并给用户持久化站内通知。

**5. 批量接口以逐单结果为准，不以整批成功为准**

部分失败不等于全部失败。前端保留原请求编号，网络中断或 503 时"恢复原批次继续处理"，不允许另建请求猜测结果。

## 快速开始

环境要求：Go 1.22+、Node 20.19+、MySQL 8。

    # 1. 配置数据库（复制后填写自己的连接，不要提交 .env.local）
    cp 04_共用后端/.env.example 04_共用后端/.env.local

    # 2. 应用迁移（会先备份，只迁移不 seed）
    .\04_共用后端\scripts\backend.ps1 -Action Migrate

    # 3. 启动后端与三端
    .\scripts\服务管理.ps1 -Action Start

    # 4. 检查互通
    .\scripts\检查互通.ps1

访问：

| 端 | 地址 |
| --- | --- |
| 商家端 | http://127.0.0.1:5173/admin/workbench |
| 用户端 | http://127.0.0.1:5174/user |
| 骑手端 | http://127.0.0.1:5175/delivery/tasks |
| 后端健康检查 | http://127.0.0.1:18090/healthz |

## 关于 AI 协同开发

仓库每个端都有 `AGENTS.md`，本质是**给 AI 编程助手立的规矩**，例如：

- 金额用整数分，禁止浮点元参与存储与结算
- 建单 / 支付 / 退款 / 派单必须走应用服务与事务，禁止通用 PATCH
- 取消订单遇支付 UNKNOWN 不得推定未付并释放库存
- 前端不展示虚构数字，报表必须来自 MySQL 聚合，演示数据必须打 `is_demo` 标识
- 修改后必须实际运行 `go test ./...` 与 `npm run build`，不得编造通过

我先定义约束和验收标准，AI 负责实现，关键路径（幂等、金额、状态迁移）逐行复核。
